# Sources

Every rule in SKILL.md traces to one of these. If a rule isn't here, it doesn't belong in
the skill.

## Google developer documentation style guide

https://developers.google.com/style (CC BY 4.0, last updated April 2026)

Used pages:

- Highlights: https://developers.google.com/style/highlights (second person, active voice,
  conditions before instructions, sentence case, numbered vs bulleted lists, code font,
  bold for UI elements, descriptive link text, don't pre-announce)
- Avoid excessive claims: https://developers.google.com/style/excessive-claims
  (no superlatives; performance claims must reference their source; careful with ensure/
  guarantee; comparative claims about other products need a linked comparison)
- Paragraph structure: https://developers.google.com/style/paragraph-structure (one idea
  per paragraph, critical information first, 5–6 sentences is the warning line)
- Voice and tone: https://developers.google.com/style/tone (conversational, not cutesy,
  reader may be in a hurry, avoid buzzwords and jargon)
- Active voice: https://developers.google.com/style/voice
- Future features: https://developers.google.com/style/future
- Timeless documentation: https://developers.google.com/style/timeless-documentation
- Text formatting summary: https://developers.google.com/style/text-formatting

Google's own recommendation on style guides (https://developers.google.com/tech-writing/
resources): do not write your own house style guide; adopt Google's or Microsoft's. This
skill follows that advice. It is a selection, not a new guide.

## Google Technical Writing One

https://developers.google.com/tech-writing/one

- Summary of the course's rules: https://developers.google.com/tech-writing/one/summary
  (define terms, consistent terminology, active voice, specific verbs, reduce "there
  is/are", one idea per sentence, eliminate unneeded words, parallel list items,
  numbered lists start with imperatives, paragraph's point in first sentence, state
  scope and audience first)
- Short sentences: https://developers.google.com/tech-writing/one/short-sentences (the
  "same rules as code" argument)
- Paragraphs: https://developers.google.com/tech-writing/one/paragraphs (3–5 sentences
  typical, >7 avoided, many one-sentence paragraphs means faulty organisation, delete
  sentences that don't relate to the paragraph topic)
- Documents: https://developers.google.com/tech-writing/one/documents (state scope and
  non-scope; state audience)

## Wikipedia: Signs of AI writing

https://en.wikipedia.org/wiki/Wikipedia:Signs_of_AI_writing

Maintained by WikiProject AI Cleanup. A descriptive catalogue of patterns observed across
thousands of detected AI-generated edits, each with real examples and, for the vocabulary
list, corroborating corpus studies (Kobak et al., Juzek & Ward, Russell, Reinhart, Geng).
Section shortcuts used: WP:AIVOCAB, WP:AINOCOPULA, WP:AICONNECT, WP:RO3, WP:AIBOLD,
WP:AILIST, WP:AIDASH, WP:AIEMOJI, WP:AICUTOFF, WP:CERTAINLY, WP:SUPERFICIAL,
WP:AIPUFFERY, WP:FACESCHALLENGES.

The page's caveat: heavy LLM users identify AI text about 90% of the time; these signs
are evidence, not proof. The skill uses them as a rewrite checklist, not a detector.

## Diátaxis

https://diataxis.fr/ and https://diataxis.fr/start-here/

Four document kinds (tutorial, how-to, reference, explanation), each with a distinct
purpose and writing mode. Used for the "name the document type first" step and the
document-type table. The relevant principle: keep the kinds separate; explanation
overloaded into a how-to or reference is the common failure.

## Microsoft Writing Style Guide

https://learn.microsoft.com/en-us/style-guide/top-10-tips-style-voice

Used only for corroboration: "get to the point fast", "lead with what's most important",
"bigger ideas, fewer words". Google recommends it as the alternative base guide.
